The bridge was restoring the old world on every session - second cause found

St Mary's ran the post-turn orphan check and found five handoffs that could not
be delivered. It was right: riverside, chester-thomas, ninn-lane, manor-house and
lower-range had all been deleted again, after this morning's save_registry fix.
All five are re-added and all seven pending handoffs now map to a live key.

The earlier diagnosis was only half the problem. mary_bridge.py loads the registry
once at startup and writes that same in-memory object back on every session start
and end, so the bridge was not merely failing to notice new jobs - it was actively
restoring the registry as it stood when it booted, every time any chat ran. That
is why re-adding by hand never survived. The loop now re-reads the registry at the
top of each pass.

What hid it: a long-running Python process keeps the module it imported at
startup. The merge fix was on disk and correct, but the live bridge is pythonw pid
31876, started 15:51:24, which is before the fix landed - so it carried on
executing the old code and the fix could not bite. That needs a restart, which I
have deliberately not done from inside a session: the bridge launches these
sessions, so killing it mid-turn would end the session doing the killing. Raised
as REQ-18 with the pid and start time so it can be confirmed.

Until that restart, expect the five jobs to be wiped again on the next session.
Every chat has been told to re-check at the end of its turn, and told that a chat
which has already run loses its whole conversation if its key goes - which is the
real argument for keeping data/jobs/<key>.md current rather than leaving it to
close-out.

- AI.md: both causes, and the standing rule that editing a file changes what the
  next process does, not what the running one is doing.
- Noticeboard and a direct reply to st-marys, whose check is the only reason this
  surfaced.
